# Testing

The suite runs with plain `cargo test` or with `cargo nextest run`, and every test passes under both. ADR-0020 records why the suite is built this way. The performance suite is separate and runs only on demand: see "The performance suite" below.

## What CI runs

`.github/workflows/ci.yml` runs on each pull request, and on demand through `workflow_dispatch`. It does not run on pushes to `main`, and it caches no build. `.github/workflows/advisories.yml` runs weekly. ADR-0020 records why.

| Job | Runs |
|---|---|
| `test-pg17` | `cargo nextest run --workspace` on `pgvector/pgvector:pg17` |
| `test-supabase` | The same on `supabase/postgres` 17.x (`GNOMON_TEST_IMAGE=supabase`) |
| `lint` | `cargo fmt --all --check`, `cargo deny check bans licenses sources`, and `cargo clippy --workspace --all-targets --all-features -- -D warnings` |
| `advisories` | `cargo deny check advisories` |

The names `test-pg17`, `test-supabase` and `lint` are the required status checks of the ruleset on `main`. A change to one of them changes the ruleset too. `advisories` is not required.

To run the dependency checks on your machine, install the version CI runs, `cargo install cargo-deny --version 0.21.0 --locked`, then run `cargo deny check`. Version 0.22 needs a newer Rust than the pinned toolchain to build. `deny.toml` holds the rules. When the advisory check in the weekly workflow does not succeed, the workflow opens an issue, or comments on the open one.

Both test jobs install the pinned Supabase CLI with Supabase's `setup-cli` action and pull their database image before the tests start, so neither download counts against a test's time limit. They set `GNOMON_TEST_SUPABASE_CLI=supabase`, so the suite runs the installed CLI. The workflow names each image itself, so a new image tag in `tests/support/server.rs` goes into `ci.yml` too. Builds leave out debug information (`CARGO_PROFILE_DEV_DEBUG=0`).

`rust-toolchain.toml` pins the Rust version, and rustup installs it on your machine as it does in CI. It is also the minimum supported Rust version: change `rust-version` in `Cargo.toml` with it. `ci.yml` sets the versions of cargo-nextest and uv on the steps that install them. The commit of `cargo-deny-action` pins the version of cargo-deny, so a new version changes that commit in `ci.yml` and `advisories.yml`, and the command above.

Lanes 3 and 4 and the performance suite run on demand. Only the performance suite asserts a time budget.

## What runs where

- `crates/gnomon/tests/alembic.rs` applies the migration files with Alembic itself, through `uvx` with Alembic, SQLAlchemy and psycopg pinned: one revision, as the README shows it, runs the files with `exec_driver_sql` and no parameters, `alembic upgrade head` applies it, and the Store accepts the schema. It runs once with pgvector in the default schema and once with an `extensions` schema, and checks that the first file created pgvector and btree_gist there.
- `crates/gnomon/tests/supabase_cli.rs` copies the files into a temporary `supabase/migrations` under timestamped names, after a consumer's own migration, and applies them with the Supabase CLI's own runner, `supabase migration up`, to a database of the suite's server, with pgvector in the default schema and in `extensions`. It needs `npx`, or an installed CLI that `GNOMON_TEST_SUPABASE_CLI` names. Its other tests are lane 3 only, ignored elsewhere. On the Supabase CLI stack they show that the CLI applied every file as `postgres`, that PostgREST reaches no gnomon table or function, and that no schema PostgREST exposes holds what the files created.
- `crates/gnomon/tests/install.rs` installs the files into a second database on the server, as a role that owns it and did not create the gnomon roles. The last file fails to hand the definer functions to `gnomon_definer`, `gnomon_writer` and `gnomon_eraser` until a role with ADMIN on all three grants the migrating role ADMIN on all three too, with neither SET nor INHERIT: ADMIN on `gnomon_definer` alone still fails on `gnomon_writer`, and ADMIN on both still fails on `gnomon_eraser`. Then the migrating role keeps no SET on any of them and the Store accepts the schema. It changes cluster-wide roles, so the step that lets the migrating role act as the three roles holds the server's lock, as does the test that no role may act as any of them.
- `crates/gnomon/tests/store_api.rs` is seam 1: the Rust core's Store API against real Postgres. `Store::connect` opens no connection, which a recording proxy shows, and a Store whose server cannot be reached connects and fails its first call with `Error::Unavailable`. `Store::check` refuses a database with no gnomon schema, a newer or half-applied chain and an embedding dimension pgvector cannot store. A failed check is not remembered: once the ledger is put right, the next call passes it. Two tests record the wire through a proxy: every call sends only unnamed statements, inside one transaction that opens with `begin; set local role ...` in one simple query and sets its claims locally, and a batch As-of read of fifty Nodes sends exactly what a read of one Node sends, it and a traversal each one Store function call in one transaction.
- `crates/gnomon/tests/connect.rs` is seam 1 for connecting: TLS with certificate verification by default, no fallback to plain text when the server refuses TLS, `sslmode=disable` refused, `sslmode=verify-full` accepted with the default verification and refused with verification off, and verification or TLS off only through an explicit setting. `Store::connect` opens no connection, so each test that needs one runs `Store::check` after it, through `support::connect_and_check`. A TLS-terminating proxy in `crates/gnomon/tests/support/tls.rs` stands in front of the test server with a certificate from a CA each test makes, because the test images run without TLS.
- `crates/gnomon/tests/pool.rs` is seam 1 for the connection pool and the public transaction (#82, ADR-0016). Calls run at once: while a transaction holds a Node's lock and a single call waits on it, a write to another Node and a read on other connections finish. A connection the server closed between two calls is replaced, and the second call succeeds. A connection the recording proxy cuts unseen fails when the next call sends its BEGIN; the Store closes it, starts the transaction once more on a new connection, and sends there exactly what a call sends, with no query to test the connection and no second schema check. With every connection held, a call fails with `Error::Unavailable` after the wait timeout. A transaction saves nothing when it is dropped or rolled back, saves everything at once when it commits, and fails its commit with `Error::RolledBack` after a call in it fails, `Error::Forbidden` from a read-only Scope and a Tenant mismatch among them. A deadlock between two transactions fails one with `Error::Conflict`, which says it can be run again. A connection the proxy cuts when COMMIT is sent fails with an unknown outcome. A call cancelled inside a transaction while it waits on a lock leaves the transaction to end, by commit or rollback, without waiting for the statement the server still runs. Last, calls are cancelled once the client has sent their first message, their second, and so on to 24: as a single call, while a transaction starts, and inside a transaction, which then cannot commit. Each is followed by another caller's call on the same pool of one connection. On every connection the proxy saw, each transaction ends before the next begins.
- `crates/gnomon/tests/concurrency.rs` runs 24 Stores at once, as users and workers. They are on 12 Tenants, two callers to a Tenant, each with its own Scope. Six raw login-role connections run beside them as bystanders. Each caller checks that it reads its own Episodes and not its sibling's in the other Scope. It also checks that a call naming another caller's Tenant fails. Each bystander checks that its transactions see no claims and no role but the login role's. On a server reached directly, the test shows Tenant isolation under concurrency. In lane 4, 30 clients share a pool of 20 server connections. There the test also shows that no role or claims outlive the call that set them.

- `crates/gnomon/tests/nodes.rs` is seam 1 for Nodes: writing a patch of property values citing an Episode, the merge order, same-transaction replacement, As-of reads and Citations.

- `crates/gnomon/tests/reserved_edge_kinds.rs` is seam 1 for the reserved Edge Kinds `same_as` and `different_from` (ADR-0012). - `crates/gnomon/tests/statements.rs` is seam 1 for Correction, End of validity and Retraction (ADR-0007): a Correction replacing the earlier Version for the same Valid time, an End of validity closing what a Version stated at the stated Valid time while it stays current at earlier valid-at instants, a Retraction stopping a Version being current, the earlier Version staying readable As-of an earlier known-at instant in each case, each statement recording its Episode, an End of validity of an Edge leaving it holding no Version whatever property values remain, and, with ranked merge on, a lower-Authority statement not ending a higher-Authority Version, staying held, and taking effect when the higher-Authority Episode's rows are deleted. - `crates/gnomon/tests/retract_episode.rs` is seam 1 for Retract Episode (ADR-0003, ADR-0007): a Retraction for every current Version, of a Node or an Edge, that only the Episode cites, no Retraction for a Version another Episode also cites (a value both state, and a Valid time split so that one half is shared), one Retraction for a Version the Episode cites twice, As-of reads before the Retraction still returning the Version with no Contribution, Citation or Episode deleted, and a second call retracting nothing. It also covers the two criteria ticket #11 names for Retract Episode: the lower-Authority Episode's held End of validity or Correction stops counting, so erasing the higher-Authority Episode's rows later leaves it without effect (a control runs the same sequence with no Retract Episode and shows it ending the plan), and, with ranked merge on, retracting a lower-Authority Episode leaves the Version a higher-Authority Episode supplied. These tests predate Erasure, so the ones that erase the higher-Authority Episode delete its rows as the operator.
- `crates/gnomon/tests/erase_episode.rs` is seam 1 for Erase Episode (ADR-0003, ADR-0007, ADR-0011, ADR-0013). Its no-residue test writes stage records and usage counts for the erased Episode and another, and an embedding of every Version's values and of two Sentences, and reads every table in the schema from the catalog and finds no row whose text holds the erased Episode's ID or a value only it stated, no row of a table that references an Episode naming it, and no row of a table derived from a Version's text (a foreign key to `gnomon.version`, apart from Citations) naming a Version the Erasure deleted or recomputed, so a table a later ticket adds fails it until Erasure deletes from it. The test gives E an Alias, which Node Kinds search, and a Sentence holding the marker, and a Sentence to the Version F alone gave an Edge, which E's write closes and the Erasure reopens; that Version stays, with no Sentence and no word of it. A full vector names no Version, so the check also finds no full vector left whose text no quantized row, Version or Sentence of its Scope uses (`support::erasure::assert_no_unused_full_vector`), and the before-and-after comparisons of `erase_graph.rs` leave the full vectors out and run that check instead. The no-residue test also writes a Summary that cites the erased Episode and is then regenerated to cite another, so a closed row cites it, and a Community that cites both. Every row that cites the erased Episode goes, closed or open, with its Citations and members, and the rows that cite the other alone stand. Each of the four is embedded for Search and has token rows of its text, and those of the two that cite the erased Episode go with them while the counts match the token rows. The Edge Version E never touches has a Sentence holding the marker that was embedded and then replaced and embedded again, so the full-vector check fails if a replaced Sentence's embedding is left.
- `crates/gnomon/tests/erase_graph.rs` is seam 1 for erasing a Node, an Edge or a Scope (ADR-0003, ADR-0005, ADR-0009, ADR-0013), and for the list of the Episodes behind a Node. Erasing an Edge removes its rows and Sentences and its bare endpoints, a bare endpoint of a Scope the caller cannot see among them, and the result names only the one the caller sees. One test runs Erase Episode, Erase Node, Erase Edge and Erase Scope on the same data, each in a transaction that rolls back, as a user of one Scope and as a user of all three, and finds the same rows left after each, with a bare Node of a Scope the first user cannot read erased and named only to the second (#83). The other tests show a write to an endpoint of an Edge the Erasure erases and a new Edge to the erased Node waiting for the Erasure, the new Edge then failing, while a write elsewhere does not wait; an Episode recorded in a Scope while its Erasure waits erased on the Store's retry; and Erasure refused without the grant and for what is already erased. - `crates/gnomon/tests/erase_oracle.rs` is the oracle test for Erasure. Random sequences of writes from up to four Episodes in two Scopes, some batched in one transaction, go to three Nodes whose Kind ranks or does not. Three Edges join the Nodes, two of them across the Scopes. Then every Episode is erased in turn, with up to three Erasures of a Node, an Edge or a Scope among them. After each Erasure an oracle that picks each property's winner from the remaining Contributions is compared with batch As-of reads of every Node at every known-at instant and with current reads. Which Edges exist is compared too, and the no-residue check of `erase_episode.rs` reads every table for the Episodes, Nodes, Edges and Versions the Erasure removed and the token and name rows of the Versions it recomputed. A second test replays the case the sequences once shrank to, where Erase Episode left a current Version it never closed without its token and name rows. The suite gives this binary eight minutes in `.config/nextest.toml` instead of three.
- `crates/gnomon/tests/stages.rs` is seam 1 for stage records (ADR-0011). A stage writes its output and its records in one transaction: a finished graph stage with usage counts and the next stage's pending record commit with a Node the transaction creates, and neither shows outside it before the commit. Every call that stores a stage's output commits it with the stage record in one transaction, and a rollback or a drop saves neither: recording an Episode with its first pending record, a Node, an Edge, a Sentence, a Version's embedding, a name's embedding, a Summary and its embedding, and a Community and its embedding, the embeddings seen through the gaps they repair. A transaction whose output is refused commits nothing, the record and an earlier write in it included. A finish whose claim was lost, because the lease of zero expired and another claim took the record, fails with `Error::StageClaimLost`, and the output rolls back with it. A claim takes a pending record, a retry due now and a running record whose lease expired, and no retry due later, no running record under a live lease, and no succeeded or failed record. Eight Stores claiming twenty-four records at once never get the same record. A claim on its own connection skips the record another claimer holds under its lock and takes the next. Without SKIP LOCKED it waits for the lock, and once the holder commits a plain FOR UPDATE skips the record and takes the next one too, so the test fails as soon as it sees the claim waiting on a lock in `pg_stat_activity`; it asserts no timing. Every lease and retry time is the database's clock, and the tests set it with a lease or a retry interval of zero, never by sleeping. Retract Episode keeps every stage record and usage count. A caller of another Scope reads, writes and claims none of the Episode's records. A stage name, model name or error code that is not an identifier is refused. Last, a catalog test reads every column of the `stage_*` tables and fails on any column that can hold model output or Episode text: a type outside uuid, the integers, boolean, timestamptz, gnomon's enums and a numeric of fixed precision, or a text column that accepts a value with a space or one of 129 characters, one more than the longest identifier the tables allow, which it probes in a rolled-back savepoint. The one text column exempt is the Episode's Scope, part of the foreign key to the Episode. The test adds a `text` column, an identifier column of up to 200 characters, a `jsonb` and a `varchar(200)` column in a rolled-back transaction and shows the check naming all four.
- `crates/gnomon/tests/full_text_search.rs` is seam 1 for the full-text branch of Search (ADR-0010). A Node is found by a word of its name, and the score of a worked example is BM25's, ln 2. Only what a Kind marks as searchable is found: a marked property, one a child Kind inherits, the name, the Aliases and an Edge Kind's marked property. A property no Kind marks is never found, and nor is a property's name. An Edge Version is found by its Sentence once one is stored. A batch of writes in one transaction is found when it commits, and a Version the batch replaced leaves no token rows. Inside the write's own transaction its words are found already, and a rolled-back write leaves none. Results honour the valid-at instant and the known-at instant, the current belief among them. A Version written on a Store's one connection is found by the next call, while no gnomon table with a pgvector column holds a row. The ranking, every score included, does not change when a Scope outside the caller's allowed set gains Versions with the query's words, while a caller who sees both Scopes ranks differently. Erasing an Episode leaves none of its words found and the BM25 counts as they were before it wrote, and the Version it reopens is found by its name. Erasing a Node lowers the counts of a Scope the caller cannot see, whose Edge it erases, and erasing a Scope leaves no count of it. Two raw transactions each write two Nodes of one Scope, the second Node of each saying the first word of the other, and neither ever waits on a lock of the other, which `pg_stat_activity` would show; four Stores writing Nodes whose names share words in one Scope at once all commit. After each of these the stored counts equal the counts the token rows give, and no committed transaction's changes to them are left, which `support::erasure::assert_search_counts_match_the_token_rows` checks. No test asserts timing.
- `crates/gnomon/tests/vector_search.rs` is seam 1 for the vector branch of Search (ADR-0010). A Version is found by its vector once the embedding-store call stores its embedding, and not before. A Refinement and a second Node with the same text in the Scope share the full vector stored first, whatever vector their own calls pass, and each Version has a quantized row of its own; the same text in another Scope has a full vector of its own, and a caller of one Scope finds only its own. The top K come back nearest first at full precision, each distance within 1e-5 of the exact cosine distance an oracle computes in the test. Results honour the valid-at and known-at instants, a Version closed by a later write after its embedding was stored among them. An Edge Version is embedded by its values, then moved to its Sentence's hash once the Sentence is stored, and a hash of neither text is refused. A wrong length, a zero vector, a NaN or infinite element, a limit below 1 and a Version the caller cannot see are refused. Recall@10 is measured on clustered synthetic 1,536-dimension vectors drawn as prototype 5 drew them: a Scope of 1,000 texts inside a Tenant whose other Scope holds 9,000 near the same subtopics, at prototype 5's "now" and its past known-at, for the small Scope and for both. The exact top 10 comes from the vectors the test generated, and each recall must be within 0.05 of prototype 5's 1.00; the test prints each value and the server's pgvector version. The plan test loads 1,000 texts in one Scope and reads `pg_stat_xact_user_tables` before and after one search in the caller's transaction: the full-vector table must be read by exactly 400 index scans fetching 400 rows and no sequential scan, at the default settings and with `enable_nestloop` off, which stands in for the planner's one-row misestimate under RLS. It fails if the re-rank's primary-key pin is dropped. No test asserts timing. Erasing an Episode deletes the quantized rows of the Versions it erases or recomputes and the full vectors only they used, and keeps a full vector a surviving Version's quantized row shares. Erasing a Node deletes the embeddings of its Edge in a Scope the caller cannot see, and keeps the full vector another Edge of that Scope shares.
- `crates/gnomon/tests/resolution.rs` is seam 1 for Resolution (ADR-0010, ADR-0012). A mention's text returns the Nodes whose current names and Aliases hold its words, ranked by BM25 per name, each with the name or Alias that matched, and a mention's embedding returns them by the stored embeddings of their names at full precision; the two halves are fused by reciprocal rank fusion with k = 60, and each candidate reports what each half found and at what rank. A name whose text already has a full vector in the Scope, a Sentence's or another Node's name, is matched by vector with no embedding stored for it, and storing a name embedding refuses a name the Node does not have now, a Node the caller cannot see, and a vector Search would refuse. - `crates/gnomon/tests/summaries.rs` is seam 1 for Summaries and Communities (ADR-0003, ADR-0014, ADR-0015). - `crates/gnomon/tests/sentences.rs` is seam 1 for storing a Sentence (ADR-0013). ## Erasure's locks and `max_locks_per_transaction`

An Erasure takes, for the rest of its transaction, the advisory lock of the Episode's ID and the Episode's row FOR UPDATE, then the advisory lock (`gnomon.node_lock_key`) of every Node and Edge the Episode touched and of both endpoints of every such Edge, in order of their IDs. Writes take the lock of the Node or Edge they write, and creating an Edge takes the locks of both endpoints in order of their IDs, so a write to an affected Node waits for the Erasure and two Erasures cannot deadlock. The header of `0005_erasure.sql` says the same.

Erasing a Node, an Edge or a Scope takes the same locks in the same order. For a Scope it first takes the advisory lock of each of its Episodes, in order of ID. Then it takes the lock of every Node and Edge it erases and of both endpoints of each such Edge, in order of their IDs, an Edge of a Scope the caller cannot see among them. Last, for a Scope, it takes its Episodes' rows FOR UPDATE. An Episode recorded in the Scope while the Erasure waits for a lock fails it with a serialization failure, and the Store retries it.

Each advisory lock is an entry in the server's shared lock table, which holds `max_locks_per_transaction * (max_connections + max_prepared_transactions)` entries for every session together. An Erasure holds one per Node, Edge and endpoint it locks, plus one for the Episode, and one transaction may hold more than `max_locks_per_transaction` while the table has room. An Erasure that needs more than the table has free fails with SQLSTATE 53200 and erases nothing. The locks are not batched, because an Erasure is one transaction. `erase_episode.rs` erases an Episode across 500 Nodes on the test images' defaults (`max_locks_per_transaction = 64`) and counts its 501 advisory locks. A deployment that erases Episodes cited across many thousands of Nodes raises the setting first. No test exceeds the table, because the suites share one server and a test that filled its lock table would fail the tests running beside it.

## Full-text Search's counts and the Sentences tests store

The token rows and BM25 counts of full-text Search are written by one trigger function, a definer that no role may execute (ADR-0009). It reads a Version under the caller's claims, so it refuses a Version those claims do not show rather than index nothing. Tests store Sentences through `gnomon.store_sentence`, as the Scope's worker with `World::store_sentence_in` or as an end user of the Scope with `support::store_sentence`.

A write records its changes to the counts in rows of its own transaction, and a deferred trigger applies them at commit in key order and deletes them. So a test that reads the counts inside the write's transaction sees them unchanged, and Search adds the transaction's own changes to them. The Erasure suites leave the counts out of their before-and-after row comparisons and recount them from the token rows instead.

## Vector Search's embeddings and the suites that load many

The functions that use pgvector keep the search path `pg_catalog, <pgvector's schema>, pg_temp` that `0004_search.sql` sets, so the suites run unchanged whether pgvector is in `public` or in `extensions`. A test that calls a pgvector function itself as the superuser looks the schema up in `pg_extension`.

The recall and plan tests load thousands of Versions through `support::vectors::load`. It inserts the Nodes and Versions as the superuser with `session_replication_role = replica`, because only that gives a Version a past Recorded time, and then stores every embedding through `gnomon.store_embedding` as the Scope's worker, so the embedding rows pass every check a caller's do. The recall test takes about 75 seconds in a debug build, most of it generating 10,000 vectors and storing them.

## Resolution's names and the suites that load many

The search index trigger writes a Node Version's name rows in the write's own transaction, so a test that inserts Versions with triggers off writes none. `support::vectors::load_names` inserts its Nodes and Versions as the superuser with `session_replication_role = replica`, as `load` does, then derives their name rows with `gnomon.index_node_names` and stores the embeddings of current names through `gnomon.store_name_embedding` as the Scope's worker. That call refuses a name the Node does not have now, so the loader stores the embeddings of replaced names as the superuser, which a search of replaced names would then find. `support::vectors::embed_every_name` stores one embedding of every current name of a Scope, and the Erasure suites use it. The no-residue check treats the name rows of a recomputed Version as it treats its token rows: they must be exactly those its name and Aliases give as they stand now.

## The performance suite

`crates/gnomon/tests/performance.rs` is on demand and apart from everything above (ticket #21, ADR-0020: no `criterion`, an on-demand suite that asserts budgets). Cargo builds it only with the `performance` feature, so a plain `cargo test` or `cargo nextest run` of the workspace never builds or runs it.

```sh
scripts/perf.sh                 # both images, then the 4 GiB case on each; about an hour on a quiet machine
scripts/perf.sh search          # fused Search at 50,000 and 200,000 visible rows, on both images
                                # (search50k and search200k run one size)
scripts/perf.sh patch           # the patch cases on a small and a large Store, on both images
scripts/perf.sh capped          # 200,000 visible rows in a container capped at 4 GiB, on both images
scripts/perf.sh words           # Search and Resolution with realistic word frequencies at 50,000 and
                                # 200,000 visible rows, then the long-text writes, on both images
                                # (words50k, words200k and writes run one of them)
PERF_IMAGES=pgvector scripts/perf.sh search

# one case, on one image, with the settings the script uses (see scripts/perf.sh)
GNOMON_TEST_CONTAINER_PREFIX=gnomon-t21 GNOMON_TEST_DATA_DIR=disk \
  cargo test -p gnomon --features performance --test performance fused_search -- --nocapture --test-threads=1
```

It asserts:

- the whole fused Search, `Caller::search` by text and vector, under 100 ms at p95 up to 50,000 visible rows and under 250 ms up to 200,000 (ADR-0010), on the data shape of prototype 5 (`origin/prototype/exact-search`);
- the same budgets for the query classes of the data set with realistic word frequencies that met them before #85 counted word frequency at query time. No class did, so each is recorded with no budget: before #85, a rare word took 150 ms at p95 at 50,000 visible rows and 665 ms at 200,000 on pgvector. #87 tracks the cost of the full-text branch with these frequencies;
- the p50 limit of each patch case on a small Store and on a large one, and that each case takes at most 1.5 times as long on the large Store as on the small one at p50 (ADR-0007, #84). The cases are bounded patches on Nodes of 10, 100 and 500 Contributions, an open-ended patch on 500, and one open-ended patch that rewrites every Version of a Node of 200 Versions. Each limit is 1.5 times the p50 the suite measured after #84 on the slower image, and ADR-0007 records them.

How a case measures:

- Search takes 10 discarded warm-up calls, then 100 timed ones, each a fresh text word and a fresh query vector near one of 200 subtopic centres. Then it times 50 more, after 5 discarded, with the word `text`, which every text holds, so the full-text branch scores every visible row. It times the full-text branch alone for that word after every second of them. Those are recorded with no budget.
- The data set with realistic word frequencies (#85) holds the same Nodes, Versions, times and vectors as the other at each size, and a Summary of every tenth Node. Each text has a name of two words and a body, 23 to 59 words in all and 41 on average, drawn from a Zipf vocabulary of 50,000 words whose commonest, `w1`, is in about 82% of the visible texts. A Node's Kind marks the body as searchable. The query words are counted over the texts visible at the current belief: a rare word is in 8 to 40 of them, and a mid word in 0.6% to 1.5%. Four query classes are timed: a rare word, a mid word, one of the three commonest words, and a natural-language question of three of the ten commonest words, a mid word and a rare word. Each takes 5 discarded calls and 50 timed ones of the whole fused Search, then as many of the full-text branch alone, with the same queries and query vectors in every run. Resolution's full-text half is timed the same way, by a mention of one of the three commonest name words and by one of a word in a name and in 8 to 40 visible texts.
- The long-text writes run on a fresh Store whose Kind marks a `text` property as searchable. They first create 200 Nodes, each with a name of two words and a text of 100 distinct words of the same vocabulary, so the Scope holds the words. Then they time 50 creates of such a Node, after 5 discarded, 50 patches that replace the text of an earlier Node, after 5 discarded, and 20 transactions that each create 25 such Nodes, after 2 discarded. Each time includes the commit. No limit is asserted.
- The patch case builds two Stores in two databases. The large one first gets 300,000 unrelated Nodes of the same Tenant and Scope, each with an Episode, two Contributions, two Versions (the first closed) and a Citation of each, inserted with set-based SQL as the superuser with `session_replication_role = replica` (`support::perf::add_unrelated_rows`). On each Store it writes, through the Store, 23 Nodes of each Contribution count and 20 Nodes of 200 Versions, one a day, each with a name of its own. Every timed write on the small Store is followed by the same write on the large one, so a change in the machine's load falls on both alike and the ratio between them holds. A bounded case takes three Nodes' worth of discarded warm-up writes, then 60 timed writes: three patches of two properties over 14 days to each of 20 Nodes. The open-ended case does the same on the Nodes of 500 Contributions, with patches from a day to the end of time. The rewrite case times one patch of a property no Version holds, from the first day to the end of time, on each Node of 200 Versions, and discards the first on each Store. It checks that the patch closed all 200 Versions and opened 201: the 200 with the new property, and one from the last day to the end of time that holds only it. Each time includes the commit.
- The data set is built with set-based SQL (`support/perf_data.sql`, `generate_series`) into a database named `gnomon_perf_<texts>_<hash of the migrations and the SQL>`, or `gnomon_perf_words_<texts>_<hash>` for realistic word frequencies. It stays on the server, so a rerun against a container that is still up skips the build. The generator is seeded and makes every ID from a row number, so a build after a change to the migrations holds the same texts, vectors, times and IDs as one before it, and the two runs measure the same data. About 54% of the texts are visible at the current belief, so 92,600 texts give about 50,000 visible rows and 370,400 give about 200,000. A case refuses to run if its data set is not within 5% of the size it names.
- The Search cases run with prototype 5's settings. `scripts/perf.sh` sets them through `GNOMON_TEST_POSTGRES_ARGS`: `shared_buffers` 8 GB, `work_mem` 64 MB, no parallel workers, `fsync` off and autovacuum off, with the tables analyzed before the Edges are written and vacuumed and frozen after the load. The capped container uses prototype 5's capped settings: `shared_buffers` 1 GB, `effective_cache_size` 3 GB, `work_mem` 16 MB. The data is loaded on one connection, because parallel callers of `gnomon.store_embedding` blocked each other on the shared full vectors and on their commits.
- The patch case and the long-text writes run on Postgres's own settings, so autovacuum analyzes what the loads write. The harness runs `analyze` after each load as well, the unrelated rows' among them. `scripts/perf.sh` turns `fsync` off for both, so they measure the writes and not the disk's flush time, which on a shared host swung each commit by up to about 100 ms (#84). Prototype 4 measured the same way, and ADR-0007's limits were set so. `PERF_PATCH_ARGS=""` runs the case with durable commits, for the record: its limits were not set for that, and a slow disk fails them. The Search cases and the patch case have their own time limits (`PERF_LIMIT_50K` 25 minutes, `PERF_LIMIT_200K` 45 minutes, `PERF_LIMIT_PATCH` 25 minutes), and so do the cases of #85 (`PERF_LIMIT_WORDS_50K` 30 minutes, `PERF_LIMIT_WORDS_200K` 75 minutes, `PERF_LIMIT_WRITES` 15 minutes), so a stuck stage fails instead of running for hours.
- In the first data set the query word is a number that one text holds. Those texts have no word-frequency structure, so the full-text branch costs less there than a real vocabulary would make it cost, which the data set with realistic word frequencies measures.

Three variables for the harness exist for this suite:

- `GNOMON_TEST_MEMORY`, such as `4g`, caps the container's memory, with no swap beyond the cap. It sets `--memory` and `--memory-swap` through the container request.
- `GNOMON_TEST_DATA_DIR=disk` keeps the data in the image's anonymous volume instead of the tmpfs the correctness suite uses, because a tmpfs would count against the cap. `scripts/perf.sh` removes the volume with the container.
- `GNOMON_TEST_POSTGRES_ARGS` appends arguments to the server's command line.

Each case writes a JSON record to `target/tmp/performance/` and prints a summary. The record holds the date, the image, the Postgres and pgvector versions, the CPU count, the host's memory, the container's memory cap (and `docker inspect`'s view of it), the server settings, the one-minute load average and the I/O pressure from `/proc/pressure/io` before and after, and the numbers. When the load average was at or above half the CPU count, or tasks waited on I/O a tenth of the time or more, the output says `THIS RUN WAS LOADED`. A budget that fails on a loaded machine is rerun when the machine is quieter. The budgets stay as they are.

Lane 3 (the Supabase CLI stack) is not needed: the `supabase/postgres` image is the server under test, and the budgets do not depend on PostgREST or the CLI's roles. The cases take a lock, so they never overlap, but the run still shares the machine with whatever else runs on it.
