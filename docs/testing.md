# Testing

The suite runs with plain `cargo test` or with `cargo nextest run`, and every test passes under both. ADR-0020 records why the suite is built this way. The performance suite is separate and runs only on demand: see "The performance suite" below.

## What runs where

- `crates/gnomon/tests/export.rs` drives `gnomon migrations export` through the binary for the plain and supabase targets. It needs no database. It shows that a re-export after a new release adds only the new migrations, with Supabase versions after every migration already in the chain, and refuses to rewrite a released one. It also compares the supabase and alembic output with the released copies in `crates/gnomon/tests/golden`, because consumers commit that output and a re-export refuses a released file that changed. A unit test in `crates/gnomon/src/migrations.rs` exports a fake newer release on every target.
- `crates/gnomon/tests/supabase_target.rs` applies the supabase export with the Supabase CLI's own runner, `supabase migration up`, to a database of the suite's server: an earlier release, then a consumer's later migration, then the new release, of which the CLI applies only the new migration. It needs `npx`.
- `crates/gnomon/tests/alembic.rs` drives the alembic target and checks the result with Alembic itself: the down-revision links `alembic history` reports, a single head, the consumer's own revisions before and after gnomon's, and `alembic upgrade head` giving a schema the Store accepts, first from an empty chain and then from an earlier release's. It needs `uvx`, and its last two tests need a database.
- `crates/gnomon/tests/supabase_cli.rs` is lane 3 only, ignored elsewhere. On the Supabase CLI stack it shows that the CLI applied every gnomon migration as `postgres`, that PostgREST reaches no gnomon table or function, and that no schema PostgREST exposes holds what the migrations created.
- `crates/gnomon/tests/store_api.rs` is seam 1: the Rust core's Store API against real Postgres. Two of its tests record the wire through a proxy: by default every call sends only unnamed statements, inside one transaction that sets its role and claims locally, and with named statements turned on each statement is prepared once per connection and reused. The second connects straight to the server, behind any pooler, because a lane's pooler may not support named statements. A third shows that a batch As-of read of fifty Nodes sends exactly what a read of one Node sends, and that it and a traversal are each one Store function call in one transaction.
- `crates/gnomon/tests/connect.rs` is seam 1 for connecting: TLS with certificate verification by default, no fallback to plain text when the server refuses TLS, `sslmode=disable` refused, and verification or TLS off only through an explicit setting. A TLS-terminating proxy in `crates/gnomon/tests/support/tls.rs` stands in front of the test server with a certificate from a CA each test makes, because the test images run without TLS.
- `crates/gnomon/tests/concurrency.rs` runs 24 Stores at once, as users and workers. They are on 12 Tenants, two callers to a Tenant, each with its own Scope. Six raw login-role connections run beside them as bystanders. Each caller checks that it reads its own Episodes and not its sibling's in the other Scope. It also checks that a call naming another caller's Tenant fails. Each bystander checks that its transactions see no claims and no role but the login role's. On a server reached directly, the test shows Tenant isolation under concurrency. In lane 4, 30 clients share a pool of 20 server connections. There the test also shows that no role or claims outlive the call that set them.
- `crates/gnomon/tests/kinds.rs` is seam 1 for Kind registration: registering and reading Kinds, and evaluating their compiled rules with `jsonb_path_match`.
- `crates/gnomon/tests/nodes.rs` is seam 1 for Nodes: writing a patch of property values citing an Episode, the merge order, same-transaction replacement, As-of reads and Citations. It ends with a smoke check that prints the p50 of a bounded patch on a Node with 100 Contributions and asserts a loose bound. The performance suite proper is `crates/gnomon/tests/performance.rs`: see "The performance suite" below.
- `crates/gnomon/tests/precision.rs` is seam 1 for bound precision (ADR-0008): a bound stored as the start of its period in UTC, an unknown start reading as open, the `uncertain` marker inside and outside an imprecise bound's period, a Refinement within the earlier period, a bound outside it recorded as a Correction, the earlier Version staying readable As-of before the statement, a later write keeping a refined bound, and a Refinement sharing the earlier Version's text hash.
- `crates/gnomon/tests/ranked_merge.rs` is seam 1 for ranked merge and Authority (ADR-0007): a higher-Authority Contribution beating a later lower one where Valid times overlap and each period keeping its own winner where they do not, equal Authority falling back to Reference time then Recorded time, an Episode with no Authority ranking as 0, a child Kind turning ranked merge on and being refused when it tries to turn it off, each Version recording the rule that chose it with a rule change leaving existing Versions alone, and a lower-Authority End of validity or bound statement losing and staying held. These tests predate Erasure: the ones that show a held statement taking effect delete the higher-Authority Episode's rows as the operator and let the Node's next write recompute its current Versions. `erase_episode.rs` shows the same through Erasure itself.
- `crates/gnomon/tests/edges.rs` is seam 1 for Edges: an Edge with no property values holding over its Valid time and citing its Episode, its values going through Contributions and Versions as a Node's do, endpoint Kinds the Edge Kind refuses, endpoints in any Scope the caller can see and none in another Tenant, each Edge Version's Sentence or none until the Store stores one, traversal As-of an instant with the neighbours' Versions then, a Node with no Versions staying while an Edge joins it, the batch As-of read of many Nodes, same-transaction replacement, and ranked merge and bound statements on Edges.
- `crates/gnomon/tests/reserved_edge_kinds.rs` is seam 1 for the reserved Edge Kinds `same_as` and `different_from` (ADR-0012, migration 0015). A fresh deployment, which has granted no one Kind registration, reads both as Edge Kinds below `edge`. Each joins `node` to `node` and is symmetric. They read the same after the Tenant registers Node Kinds of its own, and in a second Tenant that first appears after the migrations ran and registers nothing. The root Kinds and registered Kinds are not symmetric. Each reserved Kind joins Nodes of any Kinds. Creating the Edge from B to A after the one from A to B returns the same Edge, and its Version then cites both Episodes. A traversal from either Node finds it, whether it follows Edges out, in or both, while the root Kind `edge` keeps its direction. A reserved Edge from a Node to itself is refused. With the grant, Kind registration refuses either name as an Edge Kind, with a definition of its own, below another Edge Kind, or as a Node Kind. It refuses a Kind below either, and the merge-rule setter refuses both, so each reads back as before. A reserved Edge cites its Episode. A Retraction ends it, and it stays readable As-of before. Stating it again from B to A makes the same Edge hold again. Erasing the Edge removes it, and either order then addresses one new Edge. Erasing the one Episode that Edge cites erases it. Last, two Nodes joined by `same_as` each keep their own values in a read, in the batch As-of read and in a traversal.
- `crates/gnomon/tests/statements.rs` is seam 1 for Correction, End of validity and Retraction (ADR-0007): a Correction replacing the earlier Version for the same Valid time, an End of validity closing what a Version stated at the stated Valid time while it stays current at earlier valid-at instants, a Retraction stopping a Version being current, the earlier Version staying readable As-of an earlier known-at instant in each case, each statement recording its Episode, an End of validity of an Edge leaving it holding no Version whatever property values remain, and, with ranked merge on, a lower-Authority statement not ending a higher-Authority Version, staying held, and taking effect when the higher-Authority Episode's rows are deleted. These tests predate Erasure: the ones that show a held statement taking effect delete an Episode's `contribution`, `statement` and `bound_statement` rows as the operator and let the Node's next write recompute its current Versions. `erase_episode.rs` shows the same through Erasure itself.
- `crates/gnomon/tests/retract_episode.rs` is seam 1 for Retract Episode (ADR-0003, ADR-0007): a Retraction for every current Version, of a Node or an Edge, that only the Episode cites, no Retraction for a Version another Episode also cites (a value both state, and a Valid time split so that one half is shared), one Retraction for a Version the Episode cites twice, As-of reads before the Retraction still returning the Version with no Contribution, Citation or Episode deleted, and a second call retracting nothing. It also covers the two criteria ticket #11 names for Retract Episode: the lower-Authority Episode's held End of validity or Correction stops counting, so erasing the higher-Authority Episode's rows later leaves it without effect (a control runs the same sequence with no Retract Episode and shows it ending the plan), and, with ranked merge on, retracting a lower-Authority Episode leaves the Version a higher-Authority Episode supplied. These tests predate Erasure, so the ones that erase the higher-Authority Episode delete its rows as the operator.
- `crates/gnomon/tests/erase_episode.rs` is seam 1 for Erase Episode (ADR-0003, ADR-0007, ADR-0011, ADR-0013). Its no-residue test writes stage records and usage counts for the erased Episode and another, and an embedding of every Version's values and of two Sentences, and reads every table in the schema from the catalog and finds no row whose text holds the erased Episode's ID or a value only it stated, no row of a table that references an Episode naming it, and no row of a table derived from a Version's text (a foreign key to `gnomon.version`, apart from Citations) naming a Version the Erasure deleted or recomputed, so a table a later ticket adds fails it until Erasure deletes from it. The token table of full-text Search is the one such table whose rows the Store derives again: a recomputed Version that survives may keep only the token rows its text as it stands gives. The test gives E an Alias, which Node Kinds search, and a Sentence holding the marker, and a Sentence to the Version F alone gave an Edge, which E's write closes and the Erasure reopens; that Version stays, with no Sentence and no word of it. A full vector names no Version, so the check also finds no full vector left whose text no quantized row, Version or Sentence of its Scope uses (`support::erasure::assert_no_unused_full_vector`), and the before-and-after comparisons of `erase_graph.rs` leave the full vectors out and run that check instead. The other tests show surviving Versions, current and closed, recomputed from the remaining Contributions at every known-at instant; each replayed step keeping the merge rule it recorded after the Kind's rule changed; a lower-Authority End of validity that lost to the erased Episode's Correction taking effect; erasing the Episode behind a Retraction making the retracted Version current again; a Node left with no Versions erased with its last Edge, while a bare Node no Edge joins stays, and one joined by an Edge in a Scope the caller cannot see stays bare without failing the Erasure; another Episode's Retraction of a Version only the erased Episode supplied erased with it, so the remaining value holds over that Valid time again; the same Erasure removing the same rows in two runs on the same data and when the Store commits it; a write and an Edge creation on an affected Node waiting for the Erasure to commit while a write to an unaffected Node does not; the Sentence of every Edge Version the Erasure deletes or recomputes gone; a Version that a retracted Episode and the erased Episode both cite no longer current, because Erasure makes Retract Episode's choice again; an Erasure of 500 Nodes holding 501 advisory locks; and Erasure refused without the grant and for an Episode already erased. The no-residue test also writes a Summary that cites the erased Episode and is then regenerated to cite another, so a closed row cites it, and a Community that cites both. Every row that cites the erased Episode goes, closed or open, with its Citations and members, and the rows that cite the other alone stand. Each of the four is embedded for Search and has token rows of its text (migration 0020), and those of the two that cite the erased Episode go with them while the counts match the token rows. The Edge Version E never touches has a Sentence holding the marker that was embedded and then replaced and embedded again, so the full-vector check fails if a replaced Sentence's embedding is left (migration 0021).
- `crates/gnomon/tests/erase_graph.rs` is seam 1 for erasing a Node, an Edge or a Scope (ADR-0003, ADR-0005, ADR-0009, ADR-0013). Erasing an Edge removes its rows and Sentences and its bare endpoint, and leaves a bare endpoint of a Scope the caller cannot see. Erasing a Node removes its rows and every Edge that joins it, whatever the Edge's Scope, an Edge of a Scope the caller cannot see among them. It also removes a bare endpoint the caller sees, and leaves a bare endpoint of a Scope it cannot see. Erasing a Scope leaves no row in any table with a `scope` column, the stage records and usage counts of its Episodes among them, while another Scope's stay. Erasing a Node keeps the stage records of the Episodes that wrote it. It also removes every Edge of another Scope that joins one of its Nodes, and bare endpoints the caller sees. Each test runs the no-residue check of `erase_episode.rs`, which now lives in `crates/gnomon/tests/support/erasure.rs`, for the Nodes, Edges, Versions and Episodes it erased. It also compares every row of every table before and after, and finds that the only rows gone are those naming what was erased. The BM25 counts are left out of that comparison, because an Erasure lowers a count while its Scope holds other documents; instead the stored counts must equal those the token rows give. An Erasure's result names only the Edges in Scopes the caller sees, though it erases the others too. The other tests show a write to an endpoint of an Edge the Erasure erases and a new Edge to the erased Node waiting for the Erasure, the new Edge then failing, while a write elsewhere does not wait; an Episode recorded in a Scope while its Erasure waits erased on the Store's retry; and Erasure refused without the grant and for what is already erased.
- `crates/gnomon/tests/erase_oracle.rs` is the oracle test for Erasure. Random sequences of writes from up to four Episodes in two Scopes, some batched in one transaction, go to three Nodes whose Kind ranks or does not. Three Edges join the Nodes, two of them across the Scopes. Then every Episode is erased in turn, with up to three Erasures of a Node, an Edge or a Scope among them. After each Erasure an oracle that picks each property's winner from the remaining Contributions is compared with batch As-of reads of every Node at every known-at instant and with current reads. Which Edges exist is compared too, and the no-residue check of `erase_episode.rs` reads every table for the Episodes, Nodes, Edges and Versions the Erasure removed and the token and name rows of the Versions it recomputed. A failing sequence shrinks to a short one; `PROPTEST_RNG_SEED` fixes the sequences. A second test replays the case the sequences once shrank to, where Erase Episode left a current Version it never closed without its token and name rows. The suite gives this binary eight minutes in `.config/nextest.toml` instead of three.
- `crates/gnomon/tests/vacuum.rs` is seam 1 for the vacuum call after Erasure (ADR-0003, migration 0013). It counts dead tuples with `pgstattuple`, which reads the pages themselves, so no statistics lag, and it turns autovacuum off on the gnomon tables of each test's database, so only the call removes what an Erasure left. An Erasure of an Episode leaves dead tuples in every table it touched, and `Store::vacuum_erasure` with the Erasure's `touched_tables` leaves none. After Erasures of an Episode Retract Episode had retracted, of a Node joined by an Edge of a Scope the caller cannot see, of an Edge and of a Scope, together they touched the Episodes, Nodes, Edges, Contributions, Versions, Citations, statements, bound statements, Retraction marks, Sentences, stage records, usage counts, the token rows and BM25 counts of full-text Search, the full vectors and quantized rows of vector Search, the name rows of Resolution, the token rows and embeddings of Summaries and Communities, and `gnomon.erasure_reach`, whose dead rows hold the erased IDs. Without the MAINTAIN grant migration 0014 gives `gnomon_maintainer` on the stage tables the call refuses, naming `gnomon.stage_record`, and with it the call leaves no dead stage row. `Store::vacuum_erasures` vacuums every one of them and leaves no dead tuple. A table a later migration adds, deleted from by a trigger and through a cascading foreign key, appears in the Erasure's `touched_tables` and among the tables the call vacuums with no change to the call. Without a MAINTAIN grant on it the call refuses and vacuums nothing, where `VACUUM` alone would skip it with a warning. The call refuses a table no Erasure touches, and the Store's caller login role, which does not hold `gnomon_maintainer`, cannot run it. Last, `pageinspect` shows that a plain call leaves the erased bytes in the free space of a page and that `VacuumMode::Full` leaves them on no page of the tables, their TOAST tables or their indexes.
- `crates/gnomon/tests/stages.rs` is seam 1 for stage records (ADR-0011, migration 0014). A Caller from `Caller::recording` writes its stage records in the transaction of its next call that can hold a stage's output: a finished graph stage with usage counts and the next stage's pending record commit with a Node the call creates. A read before it writes none, and a later call writes none again. A call whose output is refused leaves the record running with no usage, and the records go with it, so the next write on that Caller writes none. A finish whose claim was lost, because the lease of zero expired and another claim took the record, fails with `Error::StageClaimLost` and rolls the output back. A claim takes a pending record, a retry due now and a running record whose lease expired, and no retry due later, no running record under a live lease, and no succeeded or failed record. Eight Stores claiming twenty-four records at once never get the same record. A claim on its own connection skips the record another claimer holds under its lock and takes the next. Without SKIP LOCKED it waits for the lock, and once the holder commits a plain FOR UPDATE skips the record and takes the next one too, so the test fails as soon as it sees the claim waiting on a lock in `pg_stat_activity`; it asserts no timing. Every lease and retry time is the database's clock, and the tests set it with a lease or a retry interval of zero, never by sleeping. Retract Episode keeps every stage record and usage count. A caller of another Scope reads, writes and claims none of the Episode's records. A stage name, model name or error code that is not an identifier is refused. Last, a catalog test reads every column of the `stage_*` tables and fails on any column that can hold model output or Episode text: a type outside uuid, the integers, boolean, timestamptz, gnomon's enums and a numeric of fixed precision, or a text column that accepts a value with a space or one of 129 characters, one more than the longest identifier the tables allow, which it probes in a rolled-back savepoint. The one text column exempt is the Episode's Scope, part of the foreign key to the Episode. The test adds a `text` column, an identifier column of up to 200 characters, a `jsonb` and a `varchar(200)` column in a rolled-back transaction and shows the check naming all four.
- `crates/gnomon/tests/full_text_search.rs` is seam 1 for the full-text branch of Search (ADR-0010, migration 0016). A Node is found by a word of its name, and the score of a worked example is BM25's, ln 2. Only what a Kind marks as searchable is found: a marked property, one a child Kind inherits, the name, the Aliases and an Edge Kind's marked property. A property no Kind marks is never found, and nor is a property's name. An Edge Version is found by its Sentence once one is stored. A batch of writes in one transaction is found when it commits, and a Version the batch replaced leaves no token rows. Inside the write's own transaction its words are found already, and a rolled-back write leaves none. Results honour the valid-at instant and the known-at instant, the current belief among them. A Version written on a Store's one connection is found by the next call, while no gnomon table with a pgvector column holds a row. The ranking, every score included, does not change when a Scope outside the caller's allowed set gains Versions with the query's words, while a caller who sees both Scopes ranks differently. Erasing an Episode leaves none of its words found and the BM25 counts as they were before it wrote, and the Version it reopens is found by its name. Erasing a Node lowers the counts of a Scope the caller cannot see, whose Edge it erases, and erasing a Scope leaves no count of it. Two raw transactions each write two Nodes of one Scope, the second Node of each saying the first word of the other, and neither ever waits on a lock of the other, which `pg_stat_activity` would show; four Stores writing Nodes whose names share words in one Scope at once all commit. After each of these the stored counts equal the counts the token rows give, and no committed transaction's changes to them are left, which `support::erasure::assert_search_counts_match_the_token_rows` checks. No test asserts timing.
- `crates/gnomon/tests/vector_search.rs` is seam 1 for the vector branch of Search (ADR-0010, migration 0017). A Version is found by its vector once the embedding-store call stores its embedding, and not before. A Refinement and a second Node with the same text in the Scope share the full vector stored first, whatever vector their own calls pass, and each Version has a quantized row of its own; the same text in another Scope has a full vector of its own, and a caller of one Scope finds only its own. The top K come back nearest first at full precision, each distance within 1e-5 of the exact cosine distance an oracle computes in the test. Results honour the valid-at and known-at instants, a Version closed by a later write after its embedding was stored among them. An Edge Version is embedded by its values, then moved to its Sentence's hash once the Sentence is stored, and a hash of neither text is refused. A wrong length, a zero vector, a NaN or infinite element, a limit below 1 and a Version the caller cannot see are refused. Recall@10 is measured on clustered synthetic 1,536-dimension vectors drawn as prototype 5 drew them: a Scope of 1,000 texts inside a Tenant whose other Scope holds 9,000 near the same subtopics, at prototype 5's "now" and its past known-at, for the small Scope and for both. The exact top 10 comes from the vectors the test generated, and each recall must be within 0.05 of prototype 5's 1.00; the test prints each value and the server's pgvector version. The plan test loads 1,000 texts in one Scope and reads `pg_stat_xact_user_tables` before and after one search in the caller's transaction: the full-vector table must be read by exactly 400 index scans fetching 400 rows and no sequential scan, at the default settings and with `enable_nestloop` off, which stands in for the planner's one-row misestimate under RLS. It fails if the re-rank's primary-key pin is dropped. No test asserts timing. Erasing an Episode deletes the quantized rows of the Versions it erases or recomputes and the full vectors only they used, and keeps a full vector a surviving Version's quantized row shares. Erasing a Node deletes the embeddings of its Edge in a Scope the caller cannot see, and keeps the full vector another Edge of that Scope shares.
- `crates/gnomon/tests/resolution.rs` is seam 1 for Resolution (ADR-0010, ADR-0012, migration 0019). A mention's text returns the Nodes whose current names and Aliases hold its words, ranked by BM25 per name, each with the name or Alias that matched, and a mention's embedding returns them by the stored embeddings of their names at full precision; the two halves are fused by reciprocal rank fusion with k = 60, and each candidate reports what each half found and at what rank. A Node both halves rank second outranks one a single half ranks first, even in a call for one candidate, and another Scope's names never change a score the caller sees. A name or Alias a later write replaced matches nothing, and nor does its embedding. A name of an earlier Valid time stays current unless the mention names a valid-at instant. A property a Kind marks as searchable is found by full-text Search and never by Resolution. A Node renamed in one call is found under its new name by the next, and within one transaction, through full text, before the new name has an embedding. A name whose text already has a full vector in the Scope, a Sentence's or another Node's name, is matched by vector with no embedding stored for it, and storing a name embedding refuses a name the Node does not have now, a Node the caller cannot see, and a vector Search would refuse. Erasing an Episode deletes the name rows and full vector of an Alias only it gave and keeps a full vector another Node's name shares; erasing a Node deletes its names and their full vectors. The recall test loads 5,000 Nodes with one to three current names and some replaced ones through `support::vectors::load_names`, and compares recall@10 by Node with prototype 5's 0.97 within 0.05. The plan test counts the full-vector probes of the re-rank, 400 of one row each, with `enable_nestloop` on and off. No test asserts timing.
- `crates/gnomon/tests/summaries.rs` is seam 1 for Summaries and Communities (ADR-0003, ADR-0014, ADR-0015, migration 0018). A Summary of a Node is read with its Citations, each with an optional property and place, from the valid-at instant it was written for and not before. Regenerating it closes the old row, which a read at an earlier known-at instant still finds, and deletes nothing. A Node that an Edge of another Scope joins has one Summary in each Scope, and each Scope's caller reads only its own. A Citation of an Episode of another Scope the caller sees, of an Episode it cannot see, or none at all is refused, and so is a Summary in a Scope or of a Node the caller cannot see. A Community is read with its Nodes and Citations, and its regeneration names the Community it replaces and closes it. A Node of another Scope is refused as a Community's member even when the caller sees it, and so is a Community of no Node. Another Tenant and another Scope read neither. Retract Episode changes neither. Erase Episode removes every Summary and Community that cites the Episode, closed or open, and no other, and the tables it touched are vacuumed. Erasing a Node removes its Summaries in every Scope, one in a Scope the worker cannot see among them, and the Communities that hold it, and leaves the Summary of a Node the Erasure did not list. Erasing a Scope removes its rows and the Summaries of its Nodes in other Scopes. A Node an Erasure would leave bare stays while a Summary that cites another Episode names it. A Summary write commits the stage records its Caller is recording.
- `crates/gnomon/tests/sentences.rs` is seam 1 for storing a Sentence (ADR-0013, migration 0021). Storing one adds, removes and changes no Version row or Recorded time, and the next call finds the Edge Version by a word only the Sentence holds while no embedding exists. Inside the storing transaction its words are found already, a rolled-back store leaves no Sentence, word or count, and after a commit the BM25 counts match the token rows. Storing again replaces the text and its words, and the same text again changes nothing. A replaced Sentence's embedding goes: vector Search no longer finds the Version by the old vector, the old quantized row and full vector are gone, and the new Sentence is embedded as any other. The full vector stays while another Edge Version's quantized row or a Node's name uses the same text, and only the replaced Version's row goes. A Node Version, another Scope's Edge Version, no Version, a Sentence with no word and another Tenant are refused. A Sentence of a closed Version is stored and found at a known-at the Version held. The store commits the stage records its Caller is recording, and a refused store writes none.
- `crates/gnomon/tests/gaps.rs` is seam 1 for the gap listing (migration 0021). Each kind is listed until it is repaired: an Edge Version without a Sentence, then its Sentence's missing embedding, which an embedding of its values does not fill; Node Versions' texts and current names and Aliases without an embedding, a name a rename replaced no longer among them; a Node with a current Version and no current Summary, then the Summary's missing embedding; a Community's missing embedding; and a regenerated Summary, which only the new row lacks. Two Nodes with one name are each listed and one name embedding fills both. A bare Node and a retracted Node need no Summary. Of three generations of a Community with drifting members, erasing the Episode the current one cites lists the one it replaced, not the first, until its Nodes have a current Community again; a write that regroups Nodes, closing a Community and holding none of its Nodes, leaves no gap. Erasing an Episode lists every Edge Version it reopened or replayed for a Sentence, then for the Sentence's embedding, and nothing once both are stored; a Refinement Version is listed and the closed Version keeps its Sentence. Every listing is checked to be in the promised order: by kind, then ID, then hash. The same set lists the same way on every call, and paging with limits of 1, 3, 4, 19 and 50 gives the same list, each page before the last full and its token the last gap's key. Paging with a limit of 4 while every page adds a Node's gaps and repairs a gap ahead of the cursor and one behind it lists no gap twice and skips none that was there throughout. A caller of both Scopes listing one gets only that Scope's gaps, though the other has six kinds of its own. A Scope the caller cannot see, another Tenant and a limit below 1 are refused, and an empty Scope lists nothing with no next page.
- `crates/gnomon/tests/search.rs` is seam 1 for Search (ADR-0010, ADR-0014, ADR-0015, migration 0020). One call returns Versions, Summaries and Communities fused by reciprocal rank fusion, each with its rank, distance or score in each branch. The three share one BM25 scale, so a short text holding the word ranks before a longer one. A Summary or Community is found by full text and by vector only while its Recorded time holds the known-at instant and the valid-at instant is on or after its `as_of_valid`: a Search at a past valid-at finds none, a regenerated one is found at a known-at it held, and an embedding stored after a regeneration closed it carries the closed Recorded time. From a seed with 60 Edges the neighbourhood keeps 50, the five more mentioned and the 45 lowest Edge IDs, at depth 1, returns the same results again, and reaches an Edge one step further only at depth 2. Seeded from a Company the hub owns, depth 2 keeps the hub's same 50 Edges, the one back to the seed among them at depth 1, and no seed is ever a result. Depth 1 is the default, and 0 and 3 are refused. A `same_as` Edge is followed as any other, and both of its Nodes stay results of their own (ADR-0012). With no seeds it expands from the Node the full-text branch found, and a Node joined only to Nodes no branch found is not reached. A hub much mentioned and much connected never enters the results whatever the signal weights, and is ranked by both signals once a branch finds it. The weights move the fused order as their sums say. A branch weighted 0 adds no result, and a weight below 0 or not finite is refused. At the signals' default weight a branch's tie-break still decides. A caller of one Scope gets the same results, every score, rank and count included, after another Scope gains Edges from its Node, Episodes citing them and a Summary of its Node, while a caller of both Scopes counts them. The database suites share the harness in `crates/gnomon/tests/support`. Each test gets a fresh database, created with `CREATE DATABASE ... TEMPLATE` from a template that holds the exported migrations. The harness builds that template once per server and migration set.

## Running the database suites

You need Docker. The harness starts the server itself with testcontainers.

```sh
cargo nextest run                            # pgvector/pgvector:pg17
GNOMON_TEST_IMAGE=supabase cargo nextest run # supabase/postgres 17.x
scripts/test.sh                              # both images, one after the other
```

The container:

- is named `$GNOMON_TEST_CONTAINER_PREFIX-<image>`, with the prefix defaulting to `gnomon-test`. On a machine where several agents or projects run containers, give each its own prefix, such as `gnomon-t2`;
- publishes 5432 on `127.0.0.1` only, on an ephemeral port that Docker picks, so it never collides with another stack;
- keeps its data on a tmpfs and is removed when it stops;
- stops itself about 30 seconds after the last test process disconnects, whether the run passed, failed or was killed. A run that starts within that window reuses it.

To check that nothing is left: `docker ps -a --filter name=gnomon-test`. To remove one by hand: `docker rm -f gnomon-test-pgvector`.

## Choosing the export target

`GNOMON_TEST_TARGET` picks the export target whose own tool builds the template database. The suite then runs against a schema that tool applied.

- `plain`, the default, applies each file in one transaction.
- `supabase` exports into a temporary `supabase/migrations` and runs `supabase migration up --remote=<url>` with the pinned CLI through `npx`. Lane 3 uses it.
- `alembic` exports into a temporary Alembic project and runs `alembic upgrade head` through `uvx`, with Alembic, SQLAlchemy and psycopg pinned, so nothing is installed globally. Its `env.py` runs every pending revision in one transaction, as Alembic's own template does.

```sh
GNOMON_TEST_TARGET=alembic cargo nextest run
```

The supabase and alembic tools connect as the migration role with a password: `GNOMON_TEST_MIGRATION_PASSWORD`, or the superuser's when that is unset.

## Erasure's locks and `max_locks_per_transaction`

An Erasure takes, for the rest of its transaction, the advisory lock of the Episode's ID and the Episode's row FOR UPDATE, then the advisory lock (`gnomon.node_lock_key`) of every Node and Edge the Episode touched and of both endpoints of every such Edge, in order of their IDs. Writes take the lock of the Node or Edge they write, and creating an Edge takes the locks of both endpoints in order of their IDs, so a write to an affected Node waits for the Erasure and two Erasures cannot deadlock. Migration 0011's header says the same.

Erasing a Node, an Edge or a Scope takes the same locks in the same order (migration 0012). For a Scope it first takes the advisory lock of each of its Episodes, in order of ID. Then it takes the lock of every Node and Edge it erases and of both endpoints of each such Edge, in order of their IDs, an Edge of a Scope the caller cannot see among them. Last, for a Scope, it takes its Episodes' rows FOR UPDATE. An Episode recorded in the Scope while the Erasure waits for a lock fails it with a serialization failure, and the Store retries it.

Each advisory lock is an entry in the server's shared lock table, which holds `max_locks_per_transaction * (max_connections + max_prepared_transactions)` entries for every session together. An Erasure holds one per Node, Edge and endpoint it locks, plus one for the Episode, and one transaction may hold more than `max_locks_per_transaction` while the table has room. An Erasure that needs more than the table has free fails with SQLSTATE 53200 and erases nothing. The locks are not batched, because an Erasure is one transaction. `erase_episode.rs` erases an Episode across 500 Nodes on the test images' defaults (`max_locks_per_transaction = 64`) and counts its 501 advisory locks. A deployment that erases Episodes cited across many thousands of Nodes raises the setting first. No test exceeds the table, because the suites share one server and a test that filled its lock table would fail the tests running beside it.

## The vacuum call and transaction-mode poolers

`VACUUM` cannot run inside a transaction block, and so not inside a Store function. `Store::vacuum_erasure` and `Store::vacuum_erasures` read the tables in a short transaction of their own. Then they send each table's `VACUUM` as a simple query of one statement, outside any transaction, on the Store's connection. A deployment connects that Store as a login role of its own, which holds `gnomon_maintainer` with INHERIT and without SET, and `authenticated` for the schema check `Store::connect` runs. A server runs such a statement as a transaction of its own, which `VACUUM` accepts; a multi-statement query string would be one implicit transaction block, which it refuses.

Through a transaction-mode pooler the statement is a transaction of its own too. The pooler lends a server connection for it and takes it back when it ends. The call sets no role and no setting, because a session `SET ROLE` would outlive the statement on the pooled server connection. It runs as the login role, which inherits MAINTAIN from `gnomon_maintainer`. `vacuum.rs` runs in lane 4 like every other suite, with the maintenance Store connected through the pooler, and passes through PgBouncer with unnamed and with named statements. A pooler that held the statement in a transaction on the server would fail it with SQLSTATE 25001, `VACUUM cannot run inside a transaction block`. A deployment behind such a pooler connects the maintenance Store to the server directly.

## Full-text Search's counts and the Sentences tests store

The token rows and BM25 counts of full-text Search (migration 0016) are written by one trigger function, a definer that no role may execute (ADR-0009). It reads a Version under the caller's claims, so it refuses a Version those claims do not show rather than index nothing. Tests store Sentences through `gnomon.store_sentence` (migration 0021), as the Scope's worker with `World::store_sentence_in` or as an end user of the Scope with `support::store_sentence`.

A write records its changes to the counts in rows of its own transaction, and a deferred trigger applies them at commit in key order and deletes them. So a test that reads the counts inside the write's transaction sees them unchanged, and Search adds the transaction's own changes to them. The Erasure suites leave the counts out of their before-and-after row comparisons and recount them from the token rows instead. Before an Erasure reads the tables it touched from `pg_stat_xact_user_tables`, the Store fires that deferred trigger with `SET CONSTRAINTS gnomon.search_count_delta_apply IMMEDIATE`, so the count tables are among them. That view also counts a backend's earlier transactions until their statistics are flushed, so without the firing `vacuum.rs` passed or failed by timing.

## Vector Search's embeddings and the suites that load many

Migration 0017 names pgvector's types, operators and functions with the schema `pg_extension` gives, so the suites run unchanged whether pgvector is in `public`, as on the plain and alembic targets, or in `extensions`, as on the supabase target. A test that calls a pgvector function itself as the superuser looks the schema up the same way.

The recall and plan tests load thousands of Versions through `support::vectors::load`. It inserts the Nodes and Versions as the superuser with `session_replication_role = replica`, because only that gives a Version a past Recorded time, and then stores every embedding through `gnomon.store_embedding` as the Scope's worker, so the embedding rows pass every check a caller's do. The recall test takes about 75 seconds in a debug build, most of it generating 10,000 vectors and storing them.

## Resolution's names and the suites that load many

The search index trigger writes a Node Version's name rows in the write's own transaction (migration 0019), so a test that inserts Versions with triggers off writes none. `support::vectors::load_names` inserts its Nodes and Versions as the superuser with `session_replication_role = replica`, as `load` does, then derives their name rows with `gnomon.index_node_names` and stores the embeddings of current names through `gnomon.store_name_embedding` as the Scope's worker. That call refuses a name the Node does not have now, so the loader stores the embeddings of replaced names as the superuser, which a search of replaced names would then find. `support::vectors::embed_every_name` stores one embedding of every current name of a Scope, and the Erasure suites use it. The no-residue check treats the name rows of a recomputed Version as it treats its token rows: they must be exactly those its name and Aliases give as they stand now.

## Search's smoke check

`search.rs` ends with a smoke check of the whole fused Search (migration 0020). It loads `GNOMON_SEARCH_SMOKE_ROWS` texts, 2,000 by default, through `support::vectors::load`, derives their token rows with `gnomon.index_search_text` under the worker's claims, inserts one Edge per Node with a Citation each as the superuser with `session_replication_role = replica`, vacuums, and prints the p50 and p95 of 20 Searches, each by a name's number, a word one text holds, and an embedding. It asserts no timing, so it passes on a loaded machine. To compare with prototype 5's 66 ms p95 at 50,000 visible rows:

```sh
GNOMON_SEARCH_SMOKE_ROWS=92000 cargo test -p gnomon --test search smoke -- --nocapture
```

About 54% of the texts are visible at the current belief, so 92,000 texts give about 50,000 visible rows. The load takes longer than the 180 seconds the nextest profile allows a test, so this run uses `cargo test`.

## The performance suite

`crates/gnomon/tests/performance.rs` is on demand and apart from everything above (ticket #21, ADR-0020: no `criterion`, an on-demand suite that asserts budgets). Cargo builds it only with the `performance` feature, so a plain `cargo test` or `cargo nextest run` of the workspace never builds or runs it.

```sh
scripts/perf.sh                 # both images, then the 4 GiB case on each; about an hour on a quiet machine
scripts/perf.sh search          # fused Search at 50,000 and 200,000 visible rows, on both images
                                # (search50k and search200k run one size)
scripts/perf.sh patch           # bounded patch writes, on both images
scripts/perf.sh capped          # 200,000 visible rows in a container capped at 4 GiB, on both images
PERF_IMAGES=pgvector scripts/perf.sh search

# one case, on one image, with the settings the script uses (see scripts/perf.sh)
GNOMON_TEST_CONTAINER_PREFIX=gnomon-t21 GNOMON_TEST_DATA_DIR=disk \
  cargo test -p gnomon --features performance --test performance fused_search -- --nocapture --test-threads=1
```

It asserts:

- the whole fused Search, `Caller::search` by text and vector, under 100 ms at p95 up to 50,000 visible rows and under 250 ms up to 200,000 (ADR-0010), on the data shape of prototype 5 (`origin/prototype/exact-search`);
- a bounded patch write of about 1 to 11 ms at p50, growing with the Node's Contribution count (10, 100 and 500), as prototype 4 measured (`origin/prototype/recompute-cost`, FINDINGS.md). The ceiling asserted is 11 ms at p50 for each size, and the p50 must rise from 10 to 100 to 500 Contributions.

How a case measures:

- Search takes 10 discarded warm-up calls, then 100 timed ones, each a fresh text word and a fresh query vector near one of 200 subtopic centres. A patch write takes three Nodes' worth of discarded warm-up writes, then 60 timed writes: three bounded patches (two properties, a 14-day Valid time) to each of 20 Nodes. Each time includes the commit.
- The data set is built with set-based SQL (`support/perf_data.sql`, `generate_series`) into a database named `gnomon_perf_<texts>_<hash of the migrations and the SQL>`. It stays on the server, so a rerun against a container that is still up skips the build. About 54% of the texts are visible at the current belief, so 92,600 texts give about 50,000 visible rows and 370,400 give about 200,000. A case refuses to run if its data set is not within 5% of the size it names.
- The Search cases run with prototype 5's settings. `scripts/perf.sh` sets them through `GNOMON_TEST_POSTGRES_ARGS`: `shared_buffers` 8 GB, `work_mem` 64 MB, no parallel workers, `fsync` off and autovacuum off, with the tables analyzed before the Edges are written and vacuumed and frozen after the load. The capped container uses prototype 5's capped settings: `shared_buffers` 1 GB, `effective_cache_size` 3 GB, `work_mem` 16 MB. The data is loaded on one connection, because parallel callers of `gnomon.store_embedding` blocked each other on the shared full vectors and on their commits.
- The patch case runs on Postgres's own settings, so autovacuum analyzes what the loads write, and the harness runs `analyze` after each load as well. Set `PERF_PATCH_ARGS="-c fsync=off"` to take durable commit cost out of the numbers, as prototype 4 did. The Search cases and the patch case have their own time limits (`PERF_LIMIT_50K` 25 minutes, `PERF_LIMIT_200K` 45 minutes, `PERF_LIMIT_PATCH` 25 minutes), so a stuck stage fails instead of running for hours.
- The query word is a number that one text holds. The generated texts have no word-frequency structure, so the full-text branch costs less here than a real vocabulary would make it cost.

Three variables for the harness exist for this suite:

- `GNOMON_TEST_MEMORY`, such as `4g`, caps the container's memory, with no swap beyond the cap. It sets `--memory` and `--memory-swap` through the container request.
- `GNOMON_TEST_DATA_DIR=disk` keeps the data in the image's anonymous volume instead of the tmpfs the correctness suite uses, because a tmpfs would count against the cap. `scripts/perf.sh` removes the volume with the container.
- `GNOMON_TEST_POSTGRES_ARGS` appends arguments to the server's command line.

Each case writes a JSON record to `target/tmp/performance/` and prints a summary. The record holds the date, the image, the Postgres and pgvector versions, the CPU count, the host's memory, the container's memory cap (and `docker inspect`'s view of it), the server settings, the one-minute load average and the I/O pressure from `/proc/pressure/io` before and after, and the numbers. When the load average was at or above half the CPU count, or tasks waited on I/O a tenth of the time or more, the output says `THIS RUN WAS LOADED`. A budget that fails on a loaded machine is rerun when the machine is quieter. The budgets stay as they are.

Lane 3 (the Supabase CLI stack) is not needed: the `supabase/postgres` image is the server under test, and the budgets do not depend on PostgREST or the CLI's roles. The cases take a lock, so they never overlap, but the run still shares the machine with whatever else runs on it.
