# Versions are computed from Contributions, and Erasure recomputes history

Every property value an Episode states is stored as a Contribution: the Episode, the property, the value and its Valid time. A Version's values are chosen from the Contributions that remain, ordered by Authority, then Reference time, then Recorded time. Authority is an integer the consumer gives each Episode, defaulting to 0, and it decides only between Contributions whose Valid times overlap. Correction, End of validity, Retraction and Refinement are statements of the Episode that makes them, held the same way. Every write cites at least one Episode, and a person's edit is an Episode. Erasure deletes the erased Episode's Contributions, Citations and statements, then recomputes every Version it touched, current and closed. We chose this because Erasure must be deterministic and complete: a Version that merges several Episodes would otherwise keep an erased Episode's value, and once a losing value is thrown away nothing can restore it.

## Considered options

- Discard values that lose a merge. Erasure could then only blank a property, not bring back the next-best value.
- Re-extract from the remaining Episodes with the Pipeline after an Erasure. Not deterministic, and it costs model calls.
- A merge rule decided only in the Pipeline. Consumers that write extracted values straight to the Store would bypass it.
- An `append_only` merge rule for evidence. Evidence is held as Episodes, which are already immutable.
- For Erasure, changing old Versions in place instead of replaying history. Replay decides again what a Retraction retracts, for example when erasing one Episode leaves a Version cited only by a retracted one, and a rewrite in place would have to repeat that logic (#83).
- For Erasure, deleting history from the first time the erased Episode touched a Node or Edge, with no replay. It destroys history unrelated to the erased Episode (#83).
- A smaller recompute window for an open-ended patch (#77, #84). The merge would have to know which later Versions the patch cannot change before computing them.
- Row locks instead of advisory locks for writes and Erasure. Under the writer's policies (#81), `FOR NO KEY UPDATE` and `FOR KEY SHARE` skip a row that a role may read and may not update, such as a Node in a read-only Scope, so a write would not wait for an Erasure of it. Tried on PostgreSQL 17 (#83).

## Consequences

- Ranked merge is a rule a Kind turns on. Without it, the order is Reference time, then Recorded time. A child Kind may turn ranked merge on but not off.
- With ranked merge on, Authority ranks statements as it ranks values. A Correction, End of validity or Retraction from a lower-Authority Episode loses to the values a higher-Authority Episode supplied where their Valid times overlap. It stays held, like any losing Contribution, and takes effect if the higher-Authority Episode is erased. We added this when designing the Pipeline, because the Pipeline writes statements from Episode text it does not trust. Tickets #9 and #11 need it spelled out.
- A rule change applies to later writes only. Each Version records the rule that chose its values, and an Erasure recomputes each Version under that recorded rule, so the result does not depend on when the Erasure runs.
- As-of reads at a past known-at instant are stable except across an Erasure, which rewrites Recorded-time history as if the erased Episode never existed.
- Erasing the Episode behind a Retraction makes the retracted fact current again.
- A Node left with no Versions stays as a bare identity while any Edge joins it, and is erased with its last Edge, in whichever Scope it is, once no Summary or Community names it either. So the same request removes the same rows for every caller (ADR-0009).
- A no-op write creates no Version but adds the new Episode's Citation, so a repeated statement corroborates the Version it matches.
- A write and an Erasure serialise on each Node with a per-Node advisory lock (`pg_advisory_xact_lock`). Without it, a write could compute a Version from Contributions that an Erasure is about to delete, and that Version would carry the erased value. Both paths take the lock. An Erasure takes the locks of every Node it touches up front, in a fixed order, so two Erasures cannot deadlock. A write to an affected Node waits until the Erasure commits. Reads never wait.
- A patch recomputes the whole of each current Version it overlaps. Its window runs from the earliest start to the latest end of the current Versions whose Valid time overlaps or touches the patch's, so an open-ended patch recomputes from its start, or the start of the Version it falls in, to the end of time (#77, #84). The window stays: an open-ended patch can change every later Version, and a smaller window would need the merge to know which Versions a patch leaves alone, which it learns only by computing them.
- The merge query is built so that its cost does not depend on PostgreSQL's row estimates or on the size of the Store (#84). Every step is materialized, so each runs once. No step joins two sets of rows on a condition a misestimate could turn into a nested loop over both: the window's instants are one sorted array, a Contribution finds the segments it covers by binary search in it, each segment's winner and the Contributions that state its value come from one window function, the precision of each bound comes with its instant, and one grouping matches the candidate Versions with the Versions there are. Before this, PostgreSQL estimated one row where a Node had hundreds and repeated whole steps on a large Store, the reopening compared every closed Version with every candidate, and the bound precision searched every Contribution for each new Version.
- Patch writes have limits in the performance suite (#84). Each case is timed through the Store, with its commit, on a small Store and on one with 300,000 unrelated Nodes of the same Scope, each with an Episode and two Contributions, Versions and Citations. A case may take at most 1.5 times as long at p50 on the large Store as on the small one. Each limit is 1.5 times the p50 the suite measured after #84 on the slower of the two images, with `fsync` off, so the suite measures the merge and not the disk. On the shared test host durable commits varied by up to about 100 ms each. These limits replace the patch write budget of #1, which asked for about 1 to 11 ms at p50 rising with the Contribution count. A patch on 100 Contributions costs less than one on 10, so no limit asks a cost to grow.

  | Case | Small Store p50 | Limit | Large Store p50 | Limit |
  |---|---|---|---|---|
  | Bounded patch, 10 Contributions | 9.2 ms | 13.8 ms | 9.6 ms | 14.4 ms |
  | Bounded patch, 100 Contributions | 5.3 ms | 8.0 ms | 5.2 ms | 7.8 ms |
  | Bounded patch, 500 Contributions | 16.3 ms | 24.5 ms | 16.0 ms | 24.0 ms |
  | Open-ended patch, 500 Contributions | 44.3 ms | 66.5 ms | 44.4 ms | 66.6 ms |
  | Open-ended patch rewriting every one of 200 Versions | 225.6 ms | 338.4 ms | 239.3 ms | 359.0 ms |

  Each p50 is the slower image's in the run that set the limits. That was Supabase's in every case but the open-ended one. In two runs on each image, with each write on the small Store followed by the same write on the large one, the large Store took 0.93 to 1.12 times as long as the small one in every case. Two earlier runs that timed all of one Store before the other each had one case at 1.85 and 1.88, both on a loaded host. Before the merge was rebuilt the open-ended case took up to 2.9 times as long on the large Store, and at #81 a bounded patch on 10 Contributions took 14 to 19 ms at p50 with `fsync` off. Most of the rewrite's cost is work for each Version it rewrites: the insert, its checks, and the Search and name rows.
- Erasure cost was measured in the `prototype/recompute-cost` branch (`FINDINGS.md`), on 24,620 Nodes and 1.9 million Version rows, as a non-owner role under RLS. The data were synthetic and the numbers come from a scratch server with fsync off.
  - Erasure of one Episode cited by 2,086 Versions across 500 Nodes took 24 to 35 seconds in one transaction, and it matched an oracle on every as-of read checked. Cost grows with each affected Node's history, at about 2 ms per replay step.
  - Truncate-and-replay rewrote about 22 times more Version rows than changed. Replaying only from the earliest recorded time the erased Episode touched cut the time by 6% when the Episode was early in the history, 31% in the middle and 73% when it was late.
  - As-of reads were unaffected during an Erasure (p50 about 4 ms against 5 ms with 8 readers). After an Erasure they ran about 50% slower until the tables were vacuumed and about 20% slower afterwards. Vacuuming is Postgres's autovacuum and the operator's concern, not a gnomon call (ADR-0003).
  - The prototype found that the 500 advisory locks of one Erasure needed `max_locks_per_transaction` raised to 1024. That was wrong about the limit: the lock table is shared by every session, and one transaction may hold more than `max_locks_per_transaction` while it has room. On PostgreSQL 17 with `max_connections` 100 and the default `max_locks_per_transaction`, one transaction held 5,000 advisory locks and failed at 20,000 (#83). A larger Erasure needs a larger lock table or a different lock design.
